## 한 줄 정의
데이터를 **RAM에 두는 저장소(Redis)** 와 **디스크에 두는 저장소(MySQL)** 의 대비. 핵심은 "뭐가 더 빠른가"가 아니라 — **속도는 성질이 아니라 거래**라는 것: Redis는 용량·영속성·조회 능력을 **팔아서** 속도를 샀고, MySQL은 속도를 팔아서 그것들을 샀다. 그래서 질문은 언제나 *"이 데이터는 무엇을 팔아도 되는가"*.

## 깊은 설명

### 출발: RAM은 디스크보다 1,000배 빠르다
| | 사는 곳 | 접근 시간 | 가격(GB당) | 한 대 상한 |
|---|---|---|---|---|
| **Redis** | RAM | ~100ns | ~$5 | 수백 GB ~ 몇 TB |
| **MySQL** | 디스크(SSD) | ~100µs | ~$0.1 | 수십 TB, 붙이면 더 |

그럼 자연스러운 질문: **"왜 모든 데이터를 Redis에 안 넣나?"**
답 = **RAM에 앉는 값으로 청구서 세 장을 낸다.**

### 청구서 ① 용량·비용
RAM은 **50배 비싸고**, 한 기계에 물리적으로 꽂을 수 있는 양에 **천장**이 있다. "비싸다"와 "적게 담긴다"는 별개가 아니라 같은 축의 원인·결과.
→ 단, 이건 **정도의 문제**다. 돈을 더 쓰면 어느 정도 밀어낼 수 있다.

### 청구서 ② 휘발성 (volatility) — 돈으로 못 미는 것
RAM은 **전기가 흐르는 동안만** 내용을 유지한다. 전원이 끊기면 **0**. 디스크는 전원 없이도 자국이 남는다(비휘발성).
→ 회사 데이터 전부를 Redis에 넣었다면 **재부팅 한 번에 회사가 없어진다.**

**그럼 왜 세션은 Redis에 앉히나?** 세션이라는 데이터에 두 성질이 겹쳐 있기 때문:

| | 세션 | 주문 내역 |
|---|---|---|
| ① 수명 | 30분~2주 뒤 **어차피 만료** | **영구** |
| ② 잃었을 때 | **재생성 가능** — 재로그인하면 복구 | **복구 불가** — 세상에 사본이 없음 |

②가 결정타다. **세션은 날아가도 세상에서 사라지지 않는다** — 사용자 머릿속 비밀번호로 다시 만들면 된다.

> **RAM에 앉을 자격 = 자주 읽히고 + 잃어도 재생성 가능한 데이터.**
> 세션과 캐시가 정확히 이 조건이다.

### 청구서 ③ 조회 능력의 상실
- **Redis = key-value.** `user:1042` 라는 **열쇠를 알 때만** 꺼낸다. 값을 뒤질 수단이 없다.
- **MySQL = 테이블.** 행·열이 있고 `WHERE`로 조건 검색이 된다.

> 회원 500만 명이 전부 Redis에 있다. "지난달 가입 + 서울 거주자 목록 뽑아줘."

Redis에서 유일한 방법은 **500만 개를 전부 꺼내 애플리케이션 메모리에 올린 뒤 직접 거르는 것** = **full scan**. 대가: 500만 건이 네트워크를 타고 넘어오고, 필터링 부담이 저장소 → 애플리케이션으로 떠넘겨진다. MySQL이었으면 `WHERE` 한 줄.

### 역전: 느린 디스크가 빠른 RAM을 바른다 — 인덱스
1,000배 느린 하드웨어에 앉은 MySQL이 이 질문에선 압도적으로 이긴다. 이유는 **인덱스(index)**.

책 뒤의 **색인**과 같다. 단어를 가나다순으로 미리 정렬해둔 **별도의 표** — 1,000페이지를 넘기는 대신 색인을 펴서 "342, 588"을 보고 그 페이지만 연다. MySQL도 `city` 컬럼에 인덱스를 걸면 정렬된 구조([B-tree](b-tree.md))를 따로 유지하고, `WHERE city='서울'`에 500만 행을 훑는 대신 **3번 남짓** 타고 내려가 답에 닿는다.

> ⚠️ **2026-08-04 정정:** 이 페이지는 원래 "20번 남짓"으로 적혀 있었다. **사용자가 복습 중 `2~3번`이라고 답했고 그쪽이 맞다** — B-tree는 노드 하나에 수백 갈래가 들어가서 500만 행이면 깊이가 3 언저리다. 코치가 들고 있던 숫자가 틀렸던 것.

> ### 하드웨어가 1,000배 빨라도 접근 횟수가 167만 배 차이 나면 느린 하드웨어가 이긴다.
> **자료구조가 하드웨어를 이긴다.**

**왜 이기나 — 곱셈으로:**

| | 한 번 접근 비용 | 접근 횟수 | 합계 |
|---|---|---|---|
| Redis full scan | ~100ns (RAM, **1,000배 빠름**) | **500만 번** | **0.5초** |
| MySQL + 인덱스 | ~100µs (디스크, 느림) | **3번** | **0.3ms** |

하드웨어는 1,000배 유리한데 횟수가 **167만 배** 불리하다 → 결과는 MySQL이 **약 1,600배** 이긴다.

> 🔴 **주의(7-31·8-04 2세션 연속 걸린 지점):** *"인덱싱이 되어 있어서"* 는 이 질문의 **답이 아니다.** 그건 물건의 **이름**이고, 질문은 **왜 이기는가**였다. 답은 위 곱셈 — **접근 횟수**다. (→ [B-tree](b-tree.md)에서 3번의 정체를 팜)

**인덱스의 청구서(2026-07-31 보강 — 5일 전엔 "책 색인" 즉답만 하고 구조를 안 팠음):**
- **① 공간:** 인덱스는 원본 테이블과 **별개의 정렬된 표**로 역시 **디스크에 저장**된다. `city` 인덱스 = `("부산",55), ("서울",1042), ("서울",2087)...` 이 표가 하나 더 생긴다. 책이 1,000쪽 → 1,020쪽. 인덱스 5개면 표 5개.
- **② 쓰기 속도:** 회원 1042가 서울→부산으로 이사(`UPDATE`). 인덱스가 없으면 원본 행 **1군데**. 있으면 원본 + **인덱스 표에서 항목을 빼내 `"부산"` 자리로 옮겨 정렬 재유지**. 본문 한 줄 고쳤는데 뒤 색인 20페이지를 손보는 것. 인덱스 5개면 5번.

> **인덱스 = 읽기 속도를 사려고 `공간`과 `쓰기 속도`를 판 거래.**
> 그래서 "인덱스는 많이 걸수록 좋다"는 틀린 말이다 — 읽기가 드물고 쓰기가 폭주하는 테이블에선 **손해**다.

### 실무의 답 ①: 데이터 종류마다 집을 따로
세션은 Redis, 고객 정보는 MySQL. 각 데이터의 **수명·복구가능성·조회방식**을 보고 배치한다.

### 실무의 답 ②: 같은 데이터를 두 곳에 = 캐시(cache)
> 상품 상세가 초당 1만 번 조회된다. 상품 정보는 영구 보관+조건 검색이 필요하니 집은 MySQL이 맞다. 근데 그 1만 번이 거의 다 **같은 인기 상품 몇 개**를 묻는다.

옮기는 게 아니라 **복제**한다.

```
MySQL = source of truth (원본, 영구)
Redis = 그 앞의 캐시 (자주 읽히는 것만 복사)

요청 → Redis에 있나? ─ 있음(hit)  → 바로 반환                       (~100ns)
                    └ 없음(miss) → MySQL 조회 → Redis에 채우고 → 반환
```
인기 상품이 1만 번 중 9,900번을 먹으면 **MySQL은 100번만 맞는다.** 영속성도 잃지 않는다 — 원본은 MySQL에 그대로고, **Redis가 날아가도 다시 채워지면 그만.** 위 규칙 그대로: 캐시는 "잃어도 재생성 가능한 데이터"의 교과서적 사례.

### 캐시의 청구서: stale data와 무효화
관리자가 가격을 10,000 → 8,000원으로 내린다. **MySQL만 바뀐다.** Redis 안의 10,000원은 **아무도 안 바꿔줬다.** 요청은 hit이 나서 MySQL을 쳐다보지도 않는다 → 사용자는 계속 **10,000원**을 본다. 원본과 사본이 어긋난 상태 = **stale data**, 이 문제 = **정합성(consistency)**.

| | 세션이 날아감 | 캐시가 낡음 |
|---|---|---|
| 시스템이 하는 말 | **"모르겠다"** → 재로그인 | **"10,000원입니다"** (확신에 차서) |
| 성격 | **정직한 실패** | **자신 있는 오답** |
| 발견 | 즉시 티남 | **아무도 모른다** — 에러 로그도 안 남음 |

캐시의 진짜 대가는 "가끔 틀린다"가 아니라 **"틀린 걸 아무도 모른다"**는 것. 해법은 원본을 고칠 때 사본도 지우거나 덮어쓰는 것 = **캐시 무효화(cache invalidation)**.

> ⚠️ **주의(2026-07-29에 실제로 헷갈린 지점):** 무효화 비용은 **"Redis에 다 넣기"의 죄가 아니다.**
> | 선택 | 원본 | 무효화 문제 |
> |---|---|---|
> | A. 다 Redis에 넣기 | Redis뿐 | **없음** (사본이 없으니 어긋날 상대가 없다) |
> | B. MySQL + Redis 캐시 | MySQL | **있음** |
>
> A가 틀린 이유는 **①용량·비용 ②휘발성 ③조회 능력 상실** 세 장이다. 무효화는 **B를 골랐을 때 붙는 값**.
> **모든 청구서는 그걸 발생시킨 선택에 붙어 있어야 한다.** 엉뚱한 선택에 붙이면 새 상황에서 판단이 어긋난다.

## 내 파인만 설명 (직접 작성)
> 2026-07-29 첫 학습에서 사용자가 추론으로 도달한 것들(원문 취지 보존):

- **청구서 ①:** "빠른 만큼 비용이 비싸지 않을까? 빠른 대신 저장할 수 있는 커버리지도 적을 것 같다." → 용량·비용 축 자력.
- **청구서 ②:** "아 휘발성 메모리인가 보네." → 상황 제시(전원 뽑힌 노트북) 뒤 용어 자력 회수.
- **세션이 Redis에 앉는 이유:** *"로그인 세션은 기한이 유한하니까, 유한한 세션 기간 동안만 보관되면 되니까. 영원히 보관할 필요 없음."* → 수명 축 **자력**.
- **청구서 ③:** *"엑셀로 익스포트해서 검색해야 하나? DB처럼 WHERE로 막바로 조회는 못하지. 아니면 눈으로 하나하나 보고 찾거나."* → **full scan을 이름 없이 정확히 재발명.**
- **인덱스:** 책 비유를 주자 *"인덱싱, 목차"* 즉답.
- **실무의 답 ①:** *"실무에서는 둘 다 쓰겠지. 로그인 세션은 Redis, 고객 정보는 MySQL."* → 자력.
- **캐시 패턴:** *"인기 상품 몇 개만 Redis에 복제해두기."* → **자력 도출**(이름을 모른 채 cache-aside를 그대로 설계).
- **stale data:** 흐름 추적 힌트 2단계 뒤 *"아 수정된 값이 캐시에는 업데이트가 안 된다고?"*

### 2026-07-31 복습 (첫 간격, mastery 2→3, understood 승격)

- **배치 4/4 무힌트** (세션·검색어→Redis, 주문·프로필→MySQL). 판단 기준으로 *"날아가도 다시 생성 가능한 데이터에 한해서"* 를 **맨 앞에 세움** — 5일 전 자력으로 잡은 축이 그대로 살아 있음.
- 🎯 **청구서 귀속 교정 확인(7-29 결함 회복).** "500만 명을 MySQL 원본 + Redis 사본으로 두면?"에 **무효화**를 정확히 붙임. 사본이 존재하는 구도에서만 무효화가 생긴다는 걸 제대로 쓰고 있음.
- **청구서 ③은 자력 실패** — 배치 이유를 ①비용·②재생성 가능성으로만 설명. `WHERE`가 없다는 형태는 힌트 1단계(마케팅팀 쿼리) 뒤 회수. 단 *"검색비용이 큼"* 이라는 무른 표현 → **"비용이 커진 게 아니라 필터링 부담이 저장소→애플리케이션으로 옮겨간 것"** 으로 정밀화 필요했음.
- 🔴 **인덱스를 이름으로만 답함.** *"MySQL은 데이터 인덱싱이 되어 있기 때문"* = 동어반복. "왜 이기나"(접근 횟수)·"뭘 팔았나"(공간·쓰기) 둘 다 전무 → 위 §인덱스 청구서를 새로 깔아 보강.
- 🔴 **1차 원리 자력 발화 2세션 연속 실패.** 표(얻은 것/판 것 4줄) + 빈칸 문장까지 깔아준 뒤에야 *"Redis는 용량/비용·영속성·조회 능력을 팔아서 속도를 샀다 / MySQL은 속도를 팔아서 그것들을 샀다"* 를 완성. **"뭐가 더 좋은가는 성립 안 하는 질문"까지는 자력**, 그러나 **"이 데이터는 무엇을 팔아도 되는가"** 는 못 꺼냄 — 세션 첫 답변에서 **이미 그 질문을 쓰고 있었는데도** 자기가 쓴 걸 인식 못 함(암묵적 사용 ↔ 명시적 언어화의 간극).
- → 자력 절반·유도 절반이라 m4 아님. **m2→3, understood 승격, review_due 8-03.**

- ✅ **인덱스 청구서 무힌트 회복 — 7-31 최대 결함 해소.** *"인덱스가 있으면 수정할 때 실제 데이터와 인덱스 정보 둘 다 수정해야 함"* 을 스스로. 3일 전 동어반복(*"인덱싱이 되어 있어서"*)에서 실제 메커니즘으로 올라옴.

- 🎯 **사용자가 코치의 숫자를 교정** — 인덱스 깊이를 `2~3번`이라 답했고 **그쪽이 맞았다**(페이지의 "20번"이 틀림). → 위 §역전 정정 완료.
- ❌ **1차 원리 3세션 연속 유도 필요.** 힌트 2단계까지 가고도 못 꺼내 결국 코치가 문장을 줌.
- 🔶 **의심 축을 가격에 검**(청구서 3장 중 **유일하게 돈으로 밀 수 있는 축**) → 영업사원의 *"압축 기술로 원가 절감"* 방어에 무장해제됨. **결핍("뭐가 부족하죠?")과 거래("뭘 대가로 내줬죠?")의 차이**를 여기서 새로 세움 — 결핍으로 물으면 벤더는 언제나 빠져나간다.
- 🔶 **무효화 오배치가 열린 질문에서 재발.** 사본이 없는 구도인데 *"캐시 무효화"* 를 냄. **단 코치 책임이 큼** — 질문이 *"무엇이 어디서 어디로 옮겨가나"* 라는 **수수께끼**였다. 결함으로 승격하지 않고 **관찰만** 유지.
- → 메커니즘은 전부 나왔고 지난 결함도 메워졌으나 1차 원리 미도달 → **m3 유지, 3→7일, review_due 8-11.**

## 연결 / 철학적 질문

### 🔁 같은 저울의 세 번째 층위 (전이)
| 층위 | 빠르고 · 짧게 살고 · 좁다 | 느리고 · 오래 살고 · 넓다 |
|---|---|---|
| [클로저](closure.md) (6-21) | 콜 스택 | 힙 |
| [쿠키/세션/토큰](cookie-session-token.md) (7-27) | 웹서버 안 메모리 | 공용 저장소 |
| **여기 (7-29)** | **RAM (Redis)** | **디스크 (MySQL)** |

세 번 다 같은 저울이고, 세 번 다 답이 "빠른 쪽으로 몰아라"가 아니라 **"수명과 접근 빈도를 보고 배치하라"**였다.

### 🔗 직계 부모: [쿠키/세션/토큰](cookie-session-token.md)
7-27에 자력으로 도출한 **상태 위치 스펙트럼 3점 중 "②공용 저장소"의 정체**가 이 페이지다. 그때는 "수첩을 모든 서버가 공유하게"까지 갔고 수첩의 내부는 안 열었다.

### 🔗 무효화는 한 문제다
**"토큰은 강제 로그아웃이 안 된다"(7-27)** 와 **"캐시가 낡는다"(7-29)** 는 **정확히 같은 문제**다.
> 상태를 원본에서 떨어진 곳에 복사해두는 순간, **"원본이 바뀌었다는 소식을 사본에 어떻게 전하나"** 가 항상 따라온다. 토큰이든 캐시든 이름만 다르다.
>
> (업계 농담: *"컴퓨터 과학에 어려운 건 둘뿐 — 캐시 무효화와 이름 짓기."*)

### 🔗 홉의 진짜 원인: [프로세스 vs 스레드](process-vs-thread.md)
Redis 조회가 비싼 건 "다른 기계라서"가 아니라 더 정확히는 **다른 프로세스 = 메모리 격리의 대가**다. 같은 프로세스 안이면 포인터 한 번, 프로세스가 다르면 직렬화+네트워크. 7-27에 지식 공백으로 막혔던 지점이 이미 위키 안에 답을 갖고 있었다.

### 🎯 1차 원리 (2026-07-29·07-31·08-04 **3세션 연속 자력 실패** — 유도로만 도달)

> 🔄 **2026-08-04 방법 전환 결정.** 세 번 다 *"그 문장을 말해봐"* 로 뽑으려다 실패했다. **세 번 실패했으면 방법이 틀린 것**이므로, 앞으로는 **문장을 요구하지 않는다.** 그 원리가 없으면 못 푸는 상황만 던지고 **결정만 받는다.**
> (8-04의 QuantumStore 앵커가 그 방향이었는데, 마지막에 코치가 다시 "문장으로 써봐"로 되돌아간 것이 실수였다.)

**도달 경로(7-31에 효과가 있었던 사다리):** 지금까지 나온 걸 한 표에 늘어놓으면 **네 줄이 전부 같은 모양**이고, **공짜로 빨라진 줄이 하나도 없다.**

| 무엇 | 얻은 것 | 판 것 |
|---|---|---|
| **Redis** | 속도 | 용량·비용 / 영속성 / 조회 능력 |
| **MySQL** | 영속성 · 용량 · 조회 능력 | 속도 |
| **인덱스** | 읽기 속도 | 디스크 공간 · 쓰기 속도 |
| **캐시** | 속도 | 정합성(stale data) |
| **[클로저](closure.md)** (7-31 전이) | 상태 유지 · 캡슐화 | 메모리의 자동 회수(누수 위험) |

> **속도는 성질이 아니라 거래다.**
> Redis는 그냥 빠른 게 아니라 **용량·영속성·조회 능력을 팔아서** 속도를 샀다. MySQL은 그냥 느린 게 아니라 **속도를 팔아서** 그것들을 샀다.
> 그러니 "뭐가 더 좋은가"는 성립하지 않는 질문이고, 진짜 질문은 언제나 **"이 데이터는 무엇을 팔아도 되는가"**.

7-27의 *"상태는 제거되지 않고 이동할 뿐이다"* 와 같은 높이. 그때는 **위치**를 봤고, 여기선 **그 위치마다 무엇을 팔았는지**를 본다.

## 미해결 질문
- ✅ **인덱스는 정확히 어떻게 3번 만에 닿나?** → **2026-08-04 [B-tree](b-tree.md) 페이지 개설로 착수.** 창고 안내판 그림까지 도달(안내판 한 장에 갈림길을 수백 개 적어서 3장이면 끝). 블록·fanout·분할은 아직 미소화 — 그 페이지에서 이어감.
- **캐시 무효화를 실제로 어떻게 하나?** 원본 수정 시 delete vs update, TTL로 때우기, write-through/write-back. 어느 게 언제 맞나.
- **Redis는 정말 다 날아가나?** 영속화 옵션(RDB 스냅샷·AOF)이 있다던데, 그럼 휘발성 청구서는 얼마나 깎이나. 깎인다면 왜 여전히 원본으로 안 쓰나.
- **캐시 miss가 폭주하면?** 캐시가 비어 있는 순간(재시작 직후) 1만 요청이 전부 MySQL로 쏟아지는 건 괜찮나.
- **"수평 확장하면 Redis도 SPOF 아닌가"**(7-27 자력 발견) — 복제·클러스터로 어떻게 푸나. (→ system-design)
