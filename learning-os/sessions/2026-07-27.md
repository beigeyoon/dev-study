# 1부 — 발행 운영 세션

## 오늘의 브리핑
브리핑 없이 `/card`로 바로 진입(사용자 발동). 복습 큐는 열지 않음.
⚠️ 결과적으로 **복습 0** — 쿠키/세션/토큰(due 7-23)이 4일 밀린 채 유지.

## 진행한 것
카드 파이프라인 **첫 실전 발행 시도**. 학습이 아니라 툴 다듬기 + 발행 전략 결정 세션.

### 1. 카드 정리
- 테스트로 만든 `closure-makecounter` · `event-loop-order` 2장 삭제(소스 + dist + publish-queue).
- 큐에 **`2026-07-22-promise-all-sequential` 한 장만** 남김.

### 2. 렌더러 수정 (`scripts/lib/card-html.js`)
- **핸들 `@yooni_dev` 제거 — 질문·정답 양면 모두.** 정답 카드는 푸터 블록(border-top 포함) 통째로 삭제.
- 질문 푸터 문구 축약: `❯ 정답은 댓글에서 — 먼저 맞혀봐` → **`❯ 정답은 댓글에서`**.
- 죽은 코드 정리: `.handle`/`.card--a .foot` CSS, `handle` 파라미터 배선, `cards.config.json`의 `"handle"` 필드. 핸들 미주입 검증 테스트 추가 → **23/23 통과**.
- 캡션에서 해시태그 제거: `... 정답은 댓글에서 #자바스크립트 #비동기` → `... 정답은 댓글에서`.

### 3. 스레드 발행 전략 (결정 사항)
- **주제 = `자바스크립트`.** `프론트엔드`는 기각 — ① 내용이 런타임 공통(노드에서도 동일)이라 프론트가 아님 ② 위키가 network·os·cs까지 뻗어 있고 계정도 풀스택 지향이라 **초반에 색을 못 박으면 나중에 안 맞음.** 프론트엔드는 실제 브라우저·렌더링 카드가 나올 때로 유보.
- **본문 해시태그 없음.** 스레드는 주제=태그가 같은 시스템 + 포스트당 1개 제한이라 중복이고, 인스타식 `#A #B` 나열은 홍보 계정 신호로 읽혀 역효과.
- **소개 멘트는 본문에 넣지 않음.** 훅이 죽음. bio 또는 답글로 분리.
- **발행은 2단계: 질문 포스트 → 바로 정답 답글.**
  - 코치가 먼저 "예고 답글 후 저녁에 정답"(3단계)을 제안했으나 **사용자 반박으로 폐기**: *"누가 다시 들어와서 정답을 확인하냐, 바로 보고 싶겠지."* → 타당. 스레드는 게시 직후에 도달이 몰리고 재방문은 기대할 수 없음. 카드 자체가 "3초 안에 맞혀봐" 컨셉이라 **추측 시간은 몇 시간이 아니라 이미지를 보는 그 3초**가 맞음.

### 4. 1차 발행 시도 → 삭제
올렸더니 프로필에서 **"스레드"가 아닌 "미디어"로 보임** → 사용자가 삭제. 원인 미확정(두 갈래):
- (a) 정상 — 탭은 배타적 분류가 아니라 필터라 이미지 포스트는 양쪽에 다 뜸.
- (b) 이상 — 새 포스트가 아니라 **답글로 나감**(답글 탭으로 빠짐).
→ 재발행 시 **홈의 "새 스레드 작성"에서 시작** + 올린 직후 **스레드 탭 확인**으로 판별.

### 5. 정답 답글 멘트 확정 (A안)
`Promise.all`이 빨라서가 아니라는 반전형. 분리 호출 버전도 1초임을 보여주고 → *"차이는 await 전에 다 호출했느냐 하나. await는 시작 버튼이 아니라 기다리기 버튼."* 위키 §깊은 설명의 **"all은 편한 집계기일 뿐"** 을 그대로 옮긴 것.
(원리형 B안 = "겹침은 실행이 아니라 기다림에서" → 답글로 쓰기 아까워 **카드 후보로 승격**.)

## 막힌 지점 / 보강한 것
- **스레드 플랫폼 동작을 확정 못 함** — 미디어/스레드 탭 의미, 태그 개수 제한 현행 기준, 작성자 답글의 피드 노출 여부(정답 이미지 스포일러 위험). 전부 문서가 아니라 **실측으로만** 확인 가능. 다음 발행 때 눈으로 확인할 것.
- 사용자가 제기한 스포일러 우려(*"댓글에 바로 정답 넣으면 미리보기로 보이는 거 아니냐"*)는 미해결 상태로 남김. 노출되면 대응(가림막 면 추가), 아니면 무시.

### 6. ✅ 재발행 성공 — 스레드 1호 발행 완료
"새 스레드 작성"에서 시작하니 **스레드 탭에 정상 노출.** → 1차 시도의 원인은 (b) **답글로 나갔던 것**으로 사실상 확정. 탭은 배타적 분류가 아니라 필터라는 (a) 해석은 부수적이었고, 진짜 범인은 진입점이었음.
**교훈(다음 카드부터 고정):** 카드 발행은 반드시 홈의 "새 스레드 작성"에서 시작한다. 피드를 보다가 입력창에 쓰면 답글로 샌다.
→ 카드 `status: published` + `published: 2026-07-27`, publish-queue approved→published.

**얻은 상위 프레임(페이지에 신설):** "세션 vs 토큰"은 이분법이 아니라 **"상태를 어디에 둘까" 스펙트럼 위의 두 점**. ①웹서버 안 ②공용 저장소(Redis) ③클라이언트(토큰). → **상태는 제거되지 않는다, 이동할 뿐이다. 위치마다 청구서가 다르다.**

## 막힌 지점 / 보강한 것
- **네트워크 홉(Q5-a) — 추론 실패가 아니라 지식 공백.** "Redis = 웹서버와 별개의 기계"라는 사실 자체를 몰랐음. 사실을 주자 자릿수 감각(~100ns vs ~0.5–1ms, **5,000–10,000배**, 게다가 매 요청마다)은 스스로 도달.
- **사용자 질문이 공백을 팠다:** *"공유 저장소가 DB와는 다른 개념이야?"* → 관계형(디스크·영구·쿼리) vs 인메모리(RAM·휘발·key-value) 구분 보강. 세션이 Redis에 앉는 이유 = ①매 요청 조회 ②만료되면 사라져도 되는 휘발성.
- 🔁 **비대칭 진동 (2세션 연속 관찰, 코치 메모):** 6-24엔 무효화 약점 자력·확장 강점 누락 / 7-27엔 확장 강점 자력·무효화 약점 누락. **트레이드오프의 양 날을 동시에 못 든다.** → 8-26 복습의 m5 관문으로 등록.
